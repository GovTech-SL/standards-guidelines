# Google Docs Review Workflow: Design

**Date:** 2026-05-22
**Status:** Draft (engineering spec, not a policy document)
**Owner:** Standards and Policy Division
**Scope:** Internal workflow design. Not itself a policy document.

## 1. Problem

Reviewers of GovTech policy documents (Cabinet, line ministries, legal counsel, external advisors) do not have Git access. They cannot review Markdown via pull requests. The Standards and Policy Division needs a workflow that:

1. Renders each `.md` policy document as a formal Google Doc for review.
2. Captures reviewer comments inside the Google Doc.
3. Brings those comments back into the `.md` source as commits, with full traceability.
4. Preserves Markdown as the single source of truth (per CLAUDE.md and GOV-001).

## 2. Non-Goals

- Live two-way sync between Google Doc and Markdown. The Google Doc is a read-only render of a specific Markdown version; it is regenerated, not edited, on revision.
- Replacing Git as the audit trail. Git remains authoritative; Google Doc rounds are ephemeral artifacts referenced from commits.
- Any reviewer-facing tooling beyond standard Google Docs commenting.

## 3. Design Overview

Six-phase workflow built on three artifacts:

1. A **Google Docs template** with cover block, anchor scheme, review banner, and bound Apps Script.
2. A **Markdown-to-Apps-Script generator prompt** that converts any `.md` policy document into an Apps Script the author runs once to create the Google Doc.
3. A **comments-to-revision prompt** that converts an exported comment file plus the source `.md` into a proposed diff with per-comment rationale.

```
[.md source] --(prompt 1)--> [Apps Script] --(run)--> [Google Doc]
                                                            |
                                                       (review)
                                                            |
                                                       [comments]
                                                            |
                                                  (Export menu, Apps Script)
                                                            |
                                                  [review_RN.md file]
                                                            |
                          [.md source] + [review_RN.md] --(prompt 2)--> [diff]
                                                                          |
                                                                    (author reviews)
                                                                          |
                                                                     [git commit]
```

## 4. Google Doc Template

### 4.1 Layout

```
[Cover block]
  GovTech Sri Lanka (Pvt) Ltd.
  <Document Title>
  Document ID  ·  Version  ·  Status  ·  Classification  ·  Pillar
  Issued by Standards and Policy Division  ·  Date
  Aligned with Sri Lanka 2030 Digital Blueprint

[Review banner, coloured background]
  REVIEW DRAFT  ·  Round <N>  ·  Comments due <YYYY-MM-DD>
  Anchor codes such as [ARC-001-S4.2] are machine identifiers. Do not edit them.

[Table of contents, generated by Apps Script]

[Body]
  Section headings carry the section number from Markdown.
  Each heading is followed by a small-caps grey anchor tag on its own line:
  e.g. "1. Purpose and Scope" then "[ARC-001-S1]".

  Extension Point blocks render as bordered tables, with their own anchor.

[Footer]
  Document ID  ·  Version  ·  Page X of Y  ·  OFFICIAL
```

### 4.2 Anchor Scheme

- Every Markdown heading (any level) gets a unique anchor: `[<DOC-ID>-S<dotted-section-number>]`.
- Anchor appears in the Google Doc as a light-grey small-caps line directly under the heading.
- Anchors also appear as hidden bookmarks in the doc so the Apps Script can map any comment range back to the enclosing anchor.
- Anchors are stable across review rounds for the same Markdown structure. Inserting a new section shifts the numbering of later sections; the workflow accepts this and the round-N export records both the pre- and post-shift IDs when applicable.

### 4.3 Style

Formal government document. Serif headings, sans-serif body, A4 portrait, 2 cm margins, page numbers, footer on every page. No emoji, no em dashes, no decorative imagery. Block quotes for cited standards. Tables for Extension Points and any normative obligation matrices.

## 5. Apps Script (bound to template)

The Apps Script lives in two parts. The static **scaffold** is committed to the repo as `docs/_gdoc-template.gs` and is identical for every policy document. The **per-document manifest** is produced freshly each round by the prompt described in 6.1. The author pastes both into the same Apps Script project bound to a new (or existing, see Section 8 Phase 6) Google Doc.

Two responsibilities:

### 5.1 Document builder (`buildDocFromManifest`)

- Lives in the static scaffold.
- Input: a JSON manifest, defined as a constant in the per-document file emitted by the prompt. The manifest carries front matter, the ordered list of blocks (heading, paragraph, list, table, code, extension-point), and the anchor ID per heading.
- Output: a fully styled Google Doc in the author's Drive, in a configured `Review Drafts/<DOC-ID>/` folder.

### 5.2 Comment exporter (`exportReviewComments`)

- Added as a menu item: **GovTech Review > Export Review Comments**. Apps Script can only add top-level document menus; nesting under Extensions is not available via the API.
- Walks every comment thread via the Drive API (`Drive.Comments.list`).
- For each thread, captures:
  - Quoted (anchored) text from the doc.
  - The enclosing section anchor (resolved by walking back from the comment's start index to the most recent anchor bookmark).
  - Reviewer name, timestamp, comment body, all replies, resolution status.
- Writes a single Markdown file `<DOC-ID>_review_R<N>_<YYYY-MM-DD>.md` to the same Drive folder. Author downloads it and drops it into the repo working tree (not committed; treated as a scratch artifact unless the team decides otherwise later).

### 5.3 Export file format

```markdown
# Review Export: ARC-001 Round 1

**Document:** ARC-001 Enterprise Architecture Reference Model
**Doc Version (at review):** 0.3
**Round:** 1
**Exported:** 2026-05-22 14:30 +0530
**Reviewers:** (list of distinct reviewer names)
**Comment counts:** open 12 · resolved 4 · total 16

---

## Comment 1 · [ARC-001-S4.2] · open

**Anchor text:**
> Government agencies shall publish APIs through the NDX gateway.

**Reviewer:** S. Perera (Legal)  ·  2026-05-18 09:14
**Comment:**
Does this cover diplomatic missions? PDPA carve-out applies.

**Replies:**
- R. Fernando (Standards) 2026-05-19: Will defer to legal team.

---
```

## 6. Prompts

Both prompts live in `prompts/` at repo root and are reusable across all policy documents.

### 6.1 `prompts/md-to-gdoc-script.md`

- Input: a single Markdown policy document path.
- Behaviour: reads the `.md`, validates front matter and the GOV-001/CLAUDE.md writing rules (em dash absence, banned phrase scan, obligation language), then emits a complete `.gs` file the author pastes into Apps Script. The `.gs` embeds the manifest as a constant and calls `buildDocFromManifest`. The prompt does **not** create the Google Doc itself; it produces the script.
- Fails closed on rule violations: refuses to emit the script if banned punctuation or phrases are present, and lists each line that violates the rules.

### 6.2 `prompts/gdoc-comments-to-md-revision.md`

- Input: paths to the exported review file and the source `.md`.
- Behaviour: for each open comment, locates the target text in the `.md` using (a) the anchor section ID first, (b) the quoted text as fallback, (c) human confirmation request when both are ambiguous. Produces a proposed unified diff plus a per-comment table:

  | # | Anchor | Reviewer | Disposition | Rationale |
  |---|--------|----------|-------------|-----------|
  | 1 | S4.2 | Perera | accept (reword) | Adds PDPA carve-out clause as raised. |
  | 2 | S5.1 | Silva | defer | Out of scope for this document; logged in backlog. |

- Outputs the diff for the author to apply with `git apply` or to use as the basis for manual edits. The prompt never commits.

## 8. Six-Phase Workflow

1. **Generate.** Author runs the `md-to-gdoc-script` prompt against the target `.md`. Pastes the resulting `.gs` into a new Apps Script project bound to a new Google Doc. Runs `buildDocFromManifest`. The doc lands in `Review Drafts/<DOC-ID>/`.
2. **Distribute.** Author sets sharing to "Anyone with link: commenter" (or specific reviewers, depending on classification). Sends the link with the deadline shown in the banner.
3. **Review.** Reviewers comment in-place. The doc is not edited; the banner reminds them anchors are machine identifiers.
4. **Export.** At deadline, author runs **GovTech Review > Export Review Comments** from the doc's menu bar. Downloads the resulting `.md` file.
5. **Apply.** Author runs the `gdoc-comments-to-md-revision` prompt with both files. Reviews the proposed diff, edits as needed, applies.
6. **Close out.** Author commits the revised `.md` with a message of the form `<DOC-ID>: apply review round <N> (X addressed, Y deferred)`. Marks comments resolved in the Google Doc. If another round is needed, the author creates a **new** Google Doc for round `N+1` (new file, new sharing link, banner updated, anchors regenerated from the revised Markdown). The round-`N` doc is retained read-only for audit. This avoids stale comments and anchor drift inside a single doc.

## 9. Open Items Carried Forward (not blocking)

These do not block implementation but should be tracked:

- Whether exported review files are committed to the repo (audit trail) or kept off-repo (size/noise). Initial default: not committed.
- Whether the Apps Script should also stamp the resolved Markdown commit SHA into the Google Doc footer post-merge, to close the audit loop visually for reviewers. Initial default: out of scope for v1.
- Whether the prompts should integrate with the future `scripts/lint-prose.sh` referenced in CLAUDE.md backlog item 5. Initial default: the prompt does its own scan inline; convergence with the lint script can happen later.

## 10. Success Criteria

- One policy document (likely `ARC-001`) goes through a full round trip on this workflow without manual transcription of comments.
- Round-trip from comment export to revised `.md` commit takes less than one working day for a 30-comment review.
- No reviewer is asked to learn Git or Markdown.
- The Git log alone is sufficient to reconstruct which comments shaped which revisions.
